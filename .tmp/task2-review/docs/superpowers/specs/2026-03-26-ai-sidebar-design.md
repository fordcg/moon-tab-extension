# AI 助手侧边栏 MVP 设计

日期：2026-03-26

## 1. 目标

为当前浏览器扩展新增一个 AI 助手型页面，形态为浏览器侧边栏。该页面与现有“效率工具型”新标签页分离，第一版围绕“当前页问答”展开：在用户打开侧边栏后，自动感知当前活动页面，并基于该页面内容进行问答或执行少量受控操作。

该 MVP 的核心价值不是搜索增强，而是把项目从“新标签页替换”扩展为“浏览器内工作流助手”。

## 2. 产品定位

### 2.1 页面定位

- 新页面形态：浏览器侧边栏 AI 助手页。
- 与现有主页关系：不替代 `src/pages/newtab/`，而是新增独立入口与独立运行流。
- 核心交互：默认围绕当前页面进行理解与操作，而不是通用闲聊。

### 2.2 第一版核心任务

侧边栏打开后，用户可以直接发起以下类型请求：

- 这页讲什么
- 帮我提炼重点
- 解释当前页中的术语或段落
- 基于当前页内容回答问题
- 滚动页面到某处
- 打开当前页链接
- 切换标签
- 复制当前页信息
- 聚焦页面中的输入框

### 2.3 默认上下文

第一版默认感知以下当前页信息：

- 页面标题
- 页面 URL
- 用户当前选中文本（如果存在）
- 页面主要正文内容（以提取结果、摘要或截断正文形式提供）

## 3. 范围

### 3.1 纳入 MVP 的内容

#### A. 当前页感知

侧边栏打开时自动拉取并显示：

- 标题
- URL
- 是否存在选中文本
- 正文提取状态

正文内容不要求一开始就传输完整 HTML。第一版优先使用“正文提取 + 截断/摘要”的方式，为问答提供可控上下文。

#### B. 当前页问答

用户提问时，系统将“用户消息 + 当前页上下文”一起送入编排层，由编排层决定直接回答。回答必须显式基于当前页内容，而不是退化成纯通用聊天。

#### C. 受控操作

第一版仅支持白名单动作：

- `scroll`
- `open_link`
- `switch_tab`
- `copy`
- `focus_input`

具体能力包括：

- 滚动到顶部、底部，或向上/向下滚动一段
- 打开当前页明显链接或指定链接
- 切换到上一个/下一个标签，或切回最近标签
- 复制标题、URL、标题 + URL、当前选中文本
- 聚焦页面主输入框或主搜索框

#### D. 快捷动作

侧边栏应提供几个直接可点的快捷动作：

- 总结本页
- 提取重点
- 复制标题和链接
- 聚焦页面输入框

#### E. 错误反馈

必须明确处理并反馈以下情况：

- 当前页不可读取
- 页面正文提取失败
- 没有选中文本
- 页面没有明显输入框
- 找不到目标链接
- 操作执行失败

### 3.2 不纳入 MVP 的内容

以下内容明确排除在第一版之外：

- 任意点击按钮
- 自动填写和提交表单
- 多步代理任务链
- 跨多个标签页的复杂任务编排
- 长期记忆
- 视觉元素理解
- 完整 DOM 代理
- 删除、发布、购买、账号相关等高风险动作

## 4. 架构与模块边界

推荐将 AI 侧边栏分为 4 个模块，保持清晰边界。

### 4.1 侧边栏 UI 层

负责：

- 聊天消息列表
- 当前页上下文状态展示
- 输入框与发送按钮
- 快捷动作入口
- 操作结果反馈

不负责：

- 直接访问页面 DOM
- 直接执行浏览器控制逻辑

### 4.2 页面感知层

负责采集当前活动标签页的结构化上下文：

- 标题
- URL
- 选中文本
- 页面主要正文内容

这是后续扩展更多页面感知能力的基础边界。如果未来加入可点击元素、表单状态等，也从此层扩展。

### 4.3 助手编排层

负责：

- 组装“用户问题 + 页面上下文”
- 调用模型、skill 或本地规则
- 判断这是问答请求还是操作请求
- 返回统一结果结构：文本回答，或结构化动作指令

这是 MVP 的核心大脑层，但不直接操作页面和 UI。

### 4.4 浏览器操作层

负责执行受控动作：

- 滚动页面
- 打开链接
- 切换标签
- 复制内容
- 聚焦输入框

这层只接受结构化动作，不接受自由文本命令，以降低失控和误操作风险。

## 5. 数据流

推荐的主链路：

1. 用户打开侧边栏
2. 系统采集当前活动标签页上下文
3. UI 展示“已连接当前页面”状态
4. 用户输入问题或点击快捷动作
5. 编排层判断：回答类还是操作类
6. 如果是回答类：生成回答并回显
7. 如果是操作类：调用浏览器操作层执行，并将结果回传 UI

该链路是整个 MVP 最优先打通的闭环。

## 6. 安全边界与交互规则

### 6.1 默认只读

普通提问默认只进行页面理解与问答，不执行任何操作。

### 6.2 操作需要显式意图

只有识别到明确操作意图时，才进入操作执行路径。系统不应在回答过程中偷偷执行动作。

### 6.3 操作严格受白名单约束

第一版仅允许：

- `scroll`
- `open_link`
- `switch_tab`
- `copy`
- `focus_input`

任何不在名单中的动作都必须拒绝，并向用户说明当前版本暂不支持。

### 6.4 页面采集结果应可解释

侧边栏中应显示最小必要的上下文状态，至少包括：

- 当前页面标题
- 当前页面 URL
- 是否检测到选中文本
- 是否成功提取正文

### 6.5 操作结果必须回显

每个动作执行后，必须返回：

- 执行动作名称
- 是否成功
- 失败原因（如失败）

### 6.6 特殊页面降级处理

当遇到受限页面、浏览器内置页或无法读取正文的页面时，应优雅降级：

- 能读取标题/URL 时仍显示
- 明确说明正文不可读
- 问答能力降级
- 不伪装成正常读取成功

## 7. 功能细节

### 7.1 当前页感知呈现

侧边栏顶部建议提供一块上下文状态区域，至少显示：

- 页面标题
- 域名或完整 URL
- 已连接当前页 / 上下文已同步
- 已读取正文 / 无正文 / 读取失败
- 已检测到选中文本 / 未检测到选中文本

### 7.2 快捷动作

建议在输入区域附近放置 4 个快捷动作：

- 总结本页
- 提取重点
- 复制标题和链接
- 聚焦输入框

这些动作既是高频入口，也可以帮助第一次使用的用户理解系统能力。

### 7.3 问答回答要求

回答应尽量体现来源于当前页，例如：

- 引用当前页标题或结构
- 在上下文不足时明确提示
- 对选中文本优先使用更高权重

## 8. 测试策略

### 8.1 页面感知验证

验证是否可稳定获取：

- 标题
- URL
- 选中文本
- 主要正文

覆盖：

- 普通文章页
- 搜索结果页
- 正文很少的页面
- 受限页面

### 8.2 问答验证

验证回答是否真正依赖当前页上下文，包括：

- 总结当前页
- 提取重点
- 解释术语
- 针对当前页发问

重点在于验证上下文接入正确，而不是追求复杂推理。

### 8.3 操作验证

验证 5 类白名单动作的执行结果：

- 成功时反馈明确
- 失败时反馈明确
- 不支持动作能够被拒绝

## 9. 实施优先级

### 第一阶段：打通最小闭环

优先完成：

- 侧边栏页面骨架
- 当前页上下文采集
- 消息问答流
- 5 类白名单动作执行
- 基础状态和错误反馈

主目标是打通：

`打开侧边栏 → 读取当前页 → 提问 → 回答/执行操作 → 返回结果`

### 第二阶段：能力增强

在 MVP 闭环跑通后再增强：

- 更稳定的正文提取
- 更好的链接识别
- 更丰富快捷动作
- 与主页联动

### 第三阶段：美观个人型页面

在效率工具型主页与 AI 助手型页面稳定后，再设计和实现“美观个人型”页面。

## 10. 结论

当前最值得做的工作，不是继续堆主页功能，也不是先做美观个人型页面，而是优先实现 AI 助手侧边栏 MVP。这个版本应聚焦“当前页问答 + 少量受控操作”，以尽快验证该项目从新标签页扩展升级为浏览器助手的核心价值。
