# 主页背景连续性修复设计

- 日期：2026-04-01
- 工作目录：`D:\proj\test\.worktrees\ai-sidebar-mvp`
- 目标：修复新标签页在运行时触发窗口缩小或 AI 侧边栏打开后出现的竖向背景拼缝，使背景恢复到刷新后那种连续状态。

## 1. 问题定义

当前 warm-light 主题下，主页背景在以下两条路径都会稳定出现中轴竖向拼缝，表现为左右颜色/亮度不一致：

1. 新开页后直接缩小浏览器窗口。
2. 新开页后直接打开 AI 侧边栏。

用户补充的关键信号：

- 刷新页面后，拼缝会消失。
- 问题是运行时状态变化后出现，不是初始渲染即出现。
- 验收标准是：无论缩窗还是打开侧边栏，背景都应与刚刷新完成时一样连续；允许正常动画变化，但不能再出现竖向拼缝。

## 2. 已知代码边界

### 2.1 样式层

`src/pages/newtab/styles/index.css` 中同时存在三类背景来源：

- `body` 自身的渐变背景。
- `body::before` / `body::after` 的 fixed 伪元素叠层。
- `.homepage-bubble-layer` / `.homepage-bubble-canvas` 的 fixed 动态背景层。

该 worktree 还额外引入了 `body.is-ai-sidebar-open` 的运行时状态，并会在侧边栏打开时调整背景透明度和滤镜。

### 2.2 运行时代码

`src/pages/newtab/liquid-glass-bubble-layer.mjs` 已有：

- `ResizeObserver` + `window.resize` 的 `handleResize()`。
- 对外暴露的 `window.__HOMEPAGE_BUBBLE_LAYER__.refresh()`。

这说明代码已经考虑过尺寸同步，但当前仍可能存在以下问题之一：

- resize 后尺寸同步不完整，只更新了部分渲染参数。
- 侧边栏打开引起了布局/可视区变化，但没有触发显式 refresh。
- `body` 背景层和 bubble 层在运行时的参考坐标或覆盖关系发生偏差，造成中轴明度差异。

### 2.3 验证脚本现状

仓库根目录有 `.tmp/verify_newtab_extension.py`，但该 worktree 下目前没有同路径脚本。因此当前 worktree 缺少可直接复用的本地背景连续性验证脚本。

## 3. 根因假设

推荐优先按“运行时同步失败”处理，而不是先做纯样式遮盖。

根因优先级：

1. **首要假设：运行时 refresh 缺失或不完整**
   - 缩窗和侧边栏打开都会改变可视区或布局宽度。
   - 刷新后恢复正常，说明初始渲染链路大概率是对的，问题更像状态变化后的重新采样/重绘没有完全跟上。

2. **次要假设：fixed 背景层与 body 渐变在窄窗下发生视觉拼接**
   - warm-light 主题使用了较柔和但明度差明显的米色渐变，任何层间错位都会被放大为明显拼缝。

3. **兜底假设：当前动态 bubble 方案在该布局下无法稳定保持连续**
   - 若前两类修复都无法稳定消除拼缝，则按用户确认的后手方案，在特定场景下降级到更稳定的静态连续背景。

## 4. 方案选择

### 方案 A（采用）

先补只针对该问题的 verifier，再修运行时背景同步。

实施顺序：

1. 在 worktree 内补一个只针对该问题的 verifier。
2. verifier 必须真实触发：
   - 新开页后 resize。
   - 新开页后打开 AI 侧边栏。
3. verifier 在触发前后采样背景连续性，不再允许“未采到有效信号也通过”的 fallback。
4. 依据采样结果修复背景层 refresh / resize / 重绘链路。

**原因：** 这是最符合用户现象的路径，能避免再次出现“检查通过但真实仍割裂”的误判。

### 方案 B（不采用为主路径）

仅做 CSS 修补。

**不选原因：** 若根因是运行时重绘链路缺 refresh，这类修法只是遮症状，且容易在后续交互中再次暴露。

### 方案 C（保留兜底）

在窄窗或侧边栏打开场景下降级为静态连续背景。

**使用条件：** 只有在动态方案证据充分表明难以稳定时才采用。

## 5. 具体设计

### 5.1 验证设计

在 worktree 下补一个只针对这个问题的验证脚本（建议路径仍为 `.tmp/verify_newtab_extension.py`，但职责只聚焦背景连续性问题），不扩展为全量 smoke verifier。

新增检查原则：

1. **真实触发，不靠静态样式推断通过**
   - 场景 1：打开新标签页后主动缩小 viewport。
   - 场景 2：打开新标签页后触发 AI 侧边栏打开。

2. **采样结果必须有信号**
   - 必须采到背景中轴左右的亮度/颜色差异数据。
   - 若无法采样，直接算失败，不允许 fallback 放行。

3. **通过条件改为“连续性阈值达标”**
   - 以中轴线附近左右采样差异作为主指标。
   - resize 前后、侧边栏打开前后都要比较，保证运行时触发后没有明显突变。

4. **输出诊断信息**
   - 记录采样点位置、左右均值、差值、是否达到阈值。
   - 保留失败截图，便于后续人工核对。

### 5.2 运行时修复设计

核心目标：确保任何影响背景可视区的运行时变化后，bubble 层和基础背景层重新回到一致状态。

优先检查并修复以下链路：

1. **resize 链路**
   - 确认 `syncSize()` 不只更新 canvas 元素尺寸，也同步 renderer、camera/material 所依赖的尺寸参数。
   - 若当前 `handleResize()` 只更新尺寸但没有立即可靠重绘，则在安全位置补显式 `refresh()` 或单帧重绘。

2. **AI 侧边栏打开链路**
   - 查明 `is-ai-sidebar-open` 是在哪个控制器中切换。
   - 在侧边栏 open/close 完成后，显式调用 `window.__HOMEPAGE_BUBBLE_LAYER__.refresh()`，避免只改 body class 却不重绘背景层。
   - 若侧边栏动画是分阶段布局变化，则在最终稳定态再补一次 refresh，避免取到中间态尺寸。

3. **可视区与 fixed 层覆盖关系**
   - 检查 `.homepage-bubble-layer`、`body::before`、`body::after` 是否因为父容器宽度、overflow、transform、isolation 或 z-index 关系，在缩窗后形成左右参考系不一致。
   - 只在必要时调整样式，使所有背景层继续以统一视口为参考，而不是部分跟随内容列、部分跟随 viewport。

### 5.3 样式收敛原则

若需要改 CSS，只做与连续性直接相关的最小改动：

- 不改搜索交互样式。
- 不改 AI 业务逻辑。
- 不顺带做 warm-light 主题美术重构。
- 不新增与本问题无关的视觉特效。

### 5.4 兜底降级设计

如果动态层经验证仍无法稳定通过，则切到后手方案：

- 在窄窗或 `is-ai-sidebar-open` 状态下，弱化或暂停 bubble 动态层。
- 保留连续的静态 CSS 背景作为主视觉。
- 降级后仍需保证刷新后与交互后视觉一致，不出现中轴拼缝。

## 6. 测试与验收

### 6.1 必验场景

1. 新开页后直接缩小浏览器窗口。
2. 新开页后直接打开 AI 侧边栏。
3. 场景 1 和场景 2 连续反复执行。
4. 刷新页面后再次执行场景 1/2，确认没有只靠首帧“碰巧正常”。

### 6.2 验收标准

以下条件必须同时成立：

- 背景在 resize 后没有竖向拼缝。
- 背景在 AI 侧边栏打开后没有竖向拼缝。
- 视觉连续性与刚刷新页面后的状态一致。
- 修复没有破坏原有主页加载、搜索、设置弹窗等 smoke 主流程。

## 7. 风险与控制

### 风险 1：误把视觉问题当成单纯样式问题

**控制：** 先收紧 verifier，再依据采样结果决定修 JS 还是修 CSS。

### 风险 2：侧边栏动画过程中多次布局变化，单次 refresh 不够

**控制：** 如有必要，在 open/close 最终稳定态补一次额外 refresh，而不是只在初始切换时调用。

### 风险 3：动态层本身不稳定

**控制：** 保留用户已同意的方案 C 作为后手，但只在证据充分时启用。
