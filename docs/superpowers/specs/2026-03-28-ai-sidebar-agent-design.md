# AI Sidebar 自定义接口与聊天式 Agent 设计

## 背景

当前 `ai-sidebar-mvp` 分支已经具备侧边栏问答、页面上下文读取、基础工具调用和自定义接口接入的雏形，但整体仍然偏 MVP：

- UI 更像功能面板，不像聊天助手。
- 接口配置体验不完整，用户很难判断“是否已配置 / 是否可用 / 为什么不可用”。
- 侧边栏虽然已经能连接页面和执行部分动作，但缺少面向最终用户的产品化状态与执行可视化。
- 远程 AI 能力虽已接入，但还没有围绕“自定义接口 + 聊天式 agent + 工具执行”形成完整的体验闭环。

本轮设计的目标不是继续堆更多零散功能，而是把它提升成一个真正可用的产品形态：

> 一个聊天式浏览器 AI 助手，可配置自定义接口，支持 `responses` / `chat.completions`，能读取当前页面、调用工具、操控浏览器，并以轻量、高级、简洁的方式可视化它正在做什么。

## 产品目标

本轮目标聚焦于 **自定义接口配置体验 + 聊天式 agent 侧边栏**，并明确以下用户体验要求：

1. 用户通过简单配置即可接入自己的 AI 接口。
2. 用户能明确知道当前配置是否完整、是否可用、为什么不可用。
3. 侧边栏界面必须弱化“面板感”，强化“聊天感”。
4. AI 不仅要能对话，还要能：
   - 获取当前页面信息；
   - 调用内置工具（产品内称为“工具”，而不是开发环境意义上的 skill）；
   - 操控浏览器中的可逆动作。
5. 用户在对话过程中，需要以简洁高级的方式看到 AI 正在做什么，而不是只看到最终结果。

## 范围约束

### 本轮明确支持
- 自定义接口配置字段：
  - URL
  - API Key
  - 模型
- 协议自动识别与支持：
  - `/v1/responses`
  - `/v1/chat/completions`
- sidebar 作为聊天式 agent 的首版完整体验
- 页面理解 + 工具执行 + 浏览器操作 + 执行过程可视化

### 本轮明确不做
- 自定义请求体模板
- 自定义响应路径映射
- 多 provider 模板中心
- 高风险自动化（批量关闭标签、自动提交敏感表单等）
- 重型任务控制台式 UI
- 多工具并行调度

这样可以把项目控制在单轮可落地的范围内，避免继续停留在“功能越来越多，但产品仍像半成品”的状态。

## 信息架构

### 1. 设置页（新标签页设置弹窗）

设置弹窗继续作为唯一配置入口，不新建独立设置中心。

承担以下职责：
- 用户输入接口配置：URL / API Key / 模型
- 保存配置
- 测试连接
- 展示当前配置状态
- 展示最近一次测试结果 / 错误原因
- 控制侧边栏 AI 是否进入可用态

这样可以避免把“配置入口”分散到 sidebar 和 settings 两处。

### 2. Sidebar 未配置锁定态

当接口尚未完成有效配置时，sidebar 不进入聊天可用态，而是显示明确锁定态：

- 标题：尚未连接 AI 接口
- 说明：先完成 URL / API Key / 模型配置，再启用 AI 助手
- 主按钮：去配置 AI
- 辅助说明：配置完成后可读取页面、对话、执行浏览器动作

设计意图：避免用户打开侧边栏后感觉“像坏了”或“像半成品”。

### 3. Sidebar 配置失败异常态

当接口已填写但测试失败或运行时失败时，sidebar 不应伪装成正常问答，而应进入异常态：

- 标题：AI 接口暂时不可用
- 展示精简错误原因（超时 / 401 / 403 / 格式不兼容等）
- 主按钮：重新测试
- 次按钮：去修改配置

这样可以把“未配置”和“已配置但不可用”两种状态清楚区分。

### 4. Sidebar 可用态

只有当接口配置完整且测试通过后，sidebar 才进入真正的聊天 agent 状态。

此时顶部显示双状态：
- 页面上下文：已连接当前页面
- AI 状态：远程 AI 已就绪

运行中如远程接口异常，则 AI 状态降级为：
- 远程 AI 不可用
- 正在降级 / 请重新测试连接

## 状态机设计

建议把整个接口配置与可用性抽象成如下状态：

### `unconfigured`
条件：
- URL 为空；或
- 模型为空；或
- 从未保存过有效配置

表现：
- settings 状态卡显示“未配置”
- sidebar 锁定

### `configured`
条件：
- URL / API Key / 模型已保存
- 但尚未做测试连接

表现：
- settings 显示“已保存，待测试”
- sidebar 仍锁定，避免误认为已可用

### `valid`
条件：
- 最近一次测试连接成功

表现：
- settings 显示“连接正常”
- sidebar 解锁
- agent 可执行远程问答与工具决策

### `invalid`
条件：
- 测试连接失败

表现：
- settings 显示失败原因
- sidebar 锁定

### `degraded`
条件：
- 曾经测试成功
- 但运行时接口调用失败

表现：
- sidebar 进入异常态或轻降级态
- 允许用户重新测试连接
- 不再假装处于健康状态

## 协议支持与识别

### 支持范围
首版支持两类协议，并自动识别：

1. `/v1/responses`
2. `/v1/chat/completions`

### 识别规则
保存配置或测试连接时，根据 URL 自动识别：

- 命中 `/v1/responses` → 使用 responses adapter
- 命中 `/v1/chat/completions` → 使用 chat-completions adapter
- 其他 URL → 视为当前首版不支持

不支持时，系统明确提示：
- 当前版本仅支持 `responses` / `chat.completions`
- 需要修改为兼容接口后才能启用 sidebar AI

### 设计意图
这能避免用户进入“看起来已经配置了，但其实一直 silently fallback”的状态。

## 设置页交互设计

### 1. 基础配置区
仅保留三项输入：
- URL
- API Key
- 模型

每项有极简说明：
- URL：AI 接口地址
- API Key：鉴权密钥
- 模型：调用模型名

不加入高级 header/body/schema 配置，保持这轮范围收敛。

### 2. 保存与测试分离

设置页提供两个不同动作：

#### 保存配置
职责：
- 仅保存到存储层
- 不代表“已经可用”

#### 测试连接
职责：
1. 校验字段完整性
2. 校验 URL 格式
3. 校验权限
4. 发最小测试请求
5. 返回结构化结果

测试结果需明确展示：
- 连接成功
- 模型可用
- 接口不支持当前协议
- URL 无效
- 权限未授予
- 401 / 403 / 5xx
- 超时
- 非 JSON
- 返回结构不兼容

### 3. 状态卡片
设置页的 AI 区块增加状态卡片，而不是只用一行状态文本。

状态卡片展示：
- 未配置
- 已保存待测试
- 测试通过
- 测试失败
- 运行中降级

设计意图：让用户一眼看懂当前状态，而不是自己猜测。

## Sidebar UI 设计

## 总体目标
UI 必须像聊天产品，而不是功能面板。

### 1. 顶部轻量化
顶部只保留：
- 当前页面名称
- AI 状态指示点 / 简短状态
- 一个轻量的设置 / 更多按钮

不保留大块功能卡片压在上方。

### 2. 聊天流为主视觉
中部对话区成为核心：
- 欢迎语更像助手开场
- 默认显示 2~4 个自然语言建议问题
- 历史消息成为主内容层

### 3. 输入区轻量化
输入区域重做为聊天输入框，而非表单区：
- 更圆润
- 更轻
- 更弱边框感
- 可附一个极简工具入口或状态提示

### 4. 快捷动作产品化
快捷动作不再像“控制按钮组”，而更像：
- 开场建议
- 推荐问题
- 快速命令

文案应更自然，减少“工具面板”观感。

## Agent 能力模型

### 1. 页面理解能力
首版必须支持：
- 总结当前页面
- 提炼 3 个重点
- 解释选中内容
- 回答“这页讲什么 / 核心结论是什么”

### 2. 工具能力
在产品里统一称为“工具”，不直接使用“skill”这个术语。

#### 首版页内工具
- 总结页面
- 提取重点
- 解释选中内容
- 复制标题和链接
- 滚动到顶部 / 底部
- 聚焦输入框

#### 首版浏览器工具
- 打开链接
- 新建标签页
- 切换标签页
- 刷新当前页
- 返回上一页
- 在当前搜索目标上发起搜索

### 3. Agent 决策能力
用户输入后，AI 先做意图分类：

#### 问答型
直接回答问题

#### 工具型
调用一个或多个工具执行

#### 混合型
先解释，再执行工具

例如：
- “这个页面是干嘛的，然后帮我打开官网文档”

这一步是“聊天助手”和“面板式工具”最大的区别。

## 执行过程可视化

这是本轮必须做的关键体验。

### 目标
用户在对话过程中，能够看到 AI 正在做什么，但表现方式必须：
- 简洁
- 轻量
- 高级
- 不像控制台日志

### 呈现形式
建议采用“聊天流内的轻量工具轨迹”，而不是独立的重型任务面板。

### 三层可视化结构

#### 1. 即时状态
在消息流中显示：
- 正在思考
- 正在读取页面
- 正在分析请求
- 正在执行动作

#### 2. 执行结果
动作完成后，保留一条轻消息：
- 已读取当前页面
- 已打开新标签页
- 已切换到 GitHub 标签页
- 已复制标题链接

#### 3. 可展开轨迹
当一次任务包含多个步骤时，用户可展开查看：
- 读取页面
- 判断意图
- 调用工具
- 返回结果

默认收起，避免界面过重。

### 视觉建议
执行状态应采用轻量“状态胶囊”或“工具消息块”：
- 单行或双行
- 低对比、半透明
- 小图标 + 动作文案
- 默认信息少，细节可展开

设计目标：
- 用户能理解 agent 在行动
- UI 仍然像聊天，而不是任务面板

## 自动化权限策略

用户已选择“积极自动化”。因此首版默认执行策略为：

### 直接执行
- 页内动作
- 浏览器可逆动作
  - 打开链接
  - 新建标签页
  - 切换标签页
  - 刷新
  - 搜索
  - 返回上一页

### 暂不纳入首版的高风险动作
- 自动提交敏感表单
- 批量关闭标签页
- 登录 / 支付 / 权限修改类操作

这样既满足“像 agent 一样能做事”，又避免第一版就引入过高风险。

## 模块边界

### `src/shared/search-settings.mjs`
继续作为底层共享配置层，职责包括：
- 配置存储
- 权限请求
- timeout helper
- endpoint helper

### 新增协议适配层
建议新增：
- `src/shared/ai-runtime-adapter.mjs`

职责：
- 识别协议类型（responses / chat-completions）
- 构造测试请求
- 构造正式问答请求
- 统一解析响应
- 统一返回结构化错误与运行结果

### `src/pages/newtab/settings/index.mjs`
只负责：
- 表单交互
- 状态渲染
- 调用共享 service

### `src/pages/sidebar/*`
只负责：
- 聊天消息流
- 锁定态 / 异常态 / 可用态 UI
- 工具执行轨迹
- 调用共享 adapter + browser tool 层

### Sidebar browser tool 层
建议在 sidebar 下引入独立 browser tool 执行层，用于组织：
- 页内工具
- 浏览器工具
- 执行结果结构化返回

避免把所有工具执行逻辑继续堆在单一 controller 中。

## 首版优先级

### P0
- 配置闭环：保存 / 测试 / 状态卡
- 协议识别：responses + chat-completions
- sidebar 锁定态 / 异常态 / 可用态
- 聊天式 UI 重构
- 页面理解问答
- 基础工具执行
- 执行过程可视化

### P1
- 多步骤轨迹展开
- 更细的错误分类与诊断信息
- 更自然的建议问题
- 标签页/页面上下文切换提示

### P2
- 更多浏览器动作
- 更强的连续对话承接
- 更复杂的 agent 决策链

## 验收标准

本轮实现完成后，应达到：

1. 用户可通过 URL / API Key / 模型完成自定义接口配置。
2. 系统能自动识别 `responses` / `chat.completions`，并对不支持协议给出明确提示。
3. 用户能清楚知道当前处于：未配置 / 已保存待测试 / 可用 / 不可用 / 降级。
4. sidebar 在未配置时不再表现为“像坏了的半成品”，而是明确锁定并引导配置。
5. sidebar 在可用时表现为聊天助手，而不是功能面板。
6. AI 可以：
   - 读取页面信息；
   - 与用户沟通；
   - 调用工具；
   - 执行浏览器可逆动作。
7. 用户在执行过程中，可以用简洁高级的方式看到 AI 正在做什么。

## 实施建议

这一轮应优先围绕产品闭环推进，而不是继续堆功能点。最重要的是：

- 先把配置、状态、协议识别和聊天式 UI 做扎实；
- 再把 agent 工具能力和执行可视化补齐；
- 最后再做额外扩展。

避免再次出现“功能很多，但产品感仍然像半成品”的情况。
