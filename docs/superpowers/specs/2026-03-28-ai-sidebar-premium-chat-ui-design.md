# AI Sidebar 高级聊天助手 UI 重设计

## 背景

当前 `ai-sidebar-mvp` 分支已经完成了自定义接口配置、聊天式壳层、工具执行、执行轨迹和 degraded 状态等核心能力，但从视觉和产品感上看，sidebar 仍然偏“扩展面板”而不是“高级 AI 助手”。

用户的核心反馈是：

- 它现在还不像一个真正的 AI 对话助手；
- 不够好看，也不够高级；
- 需要更像 Arc / 浏览器 Copilot 风格，而不是工具面板；
- 页面感要弱，聊天感要强；
- 要保留“看见它在做什么”的能力，但不能像调试面板或日志控制台。

因此，这一轮不再扩功能，而是专门聚焦于 **UI / 视觉语言 / 信息层级 / 交互呈现** 的重设计。

## 目标

把当前 sidebar 从：

> 浏览器扩展里的 AI 功能侧栏

重设计为：

> 一个嵌在浏览器里的、Arc / Copilot 风格的高级聊天助手

并满足以下约束：

1. **弱页面感**：页面只是上下文，不是界面主角。
2. **聊天主导**：用户打开后应优先感受到“我在和 AI 助手聊天”。
3. **高级、克制、精致**：不是炫技式科技 UI，不是 dashboard，也不是设置面板延伸。
4. **过程可见但不吵**：执行轨迹保留，但表现为轻量系统提示而非大型任务面板。

## 视觉方向

### 参考气质
- Arc 风格的浏览器内助手
- Copilot 风格的页面协作者
- 但整体更接近高级聊天产品，而不是工具平台

### 核心关键词
- 深色
- 克制
- 微玻璃感
- 柔光
- 强留白
- 内容优先
- 高级排版
- 安静

### 明确避免
- 大面积面板块分区
- dashboard 风格信息架构
- 过亮、过硬的科技蓝紫渐变
- 重工具条、重控制区、重配置味道
- 太像“网页管理后台”或“扩展设置页”

## 信息层级

### 1. 顶部：极轻 Header
顶部只承担极少量信息：
- AI 身份感（极轻）
- 当前状态（已连接页面 / AI 已就绪 / AI 暂时不可用）
- 一个小设置入口

不再承担：
- 大标题区
- 大面积页面摘要区
- 大块状态卡

设计目标：
- 打开后先看到“助手”，而不是“系统状态面板”

### 2. 页面信息：退到背景层
因为用户选择了**弱页面感**，所以页面信息只作为上下文存在：
- 默认只展示一行轻状态
- 页面标题保留，但弱化
- URL 不再作为大面积常驻信息
- 页面详情进入低优先级折叠或二级区域

设计目标：
- AI 看起来知道你在看什么
- 但不会一直把“当前页面信息”当成主角展示

### 3. 聊天区：成为主视觉中心
消息流是整个 sidebar 的主视觉：
- 首屏欢迎语更自然
- assistant 消息权重高于状态文案
- 建议问题是“对话引导”，不是“功能按钮”
- 视觉重心落在 message flow，而不是状态卡或控制区

## 布局方案

### 顶部区域
建议重做为一条窄、轻、浮层感的顶部条：
- 左：小 AI 标记 / 助手名
- 中：一行状态文案
- 右：设置按钮

不做明显边框盒子，不做厚重卡片。

### 主体区域
分为两层：

#### A. 主聊天流
- assistant / user / tool-result / system-lite 消息统一进入消息流
- assistant 气泡更柔和、阅读感更强
- tool-result 更细、更轻、更系统化

#### B. 轻量轨迹提示
执行过程不单独占大块区域，而是：
- 作为消息流中的弱层级内容存在
- 或者作为聊天区顶部/底部的窄轨迹列短暂出现
- 可折叠，但默认不喧宾夺主

### 底部输入区
输入区做成更像高级 AI 聊天输入框，而不是网页表单：
- 薄
- 圆角更自然
- 边界更轻
- 占位文案更像聊天
- 发送按钮更克制

## 状态呈现

### 1. 锁定态（未配置 / 已保存未测试）
继续保留，但要变得更“产品化”：
- 更像一个安静的 onboarding 状态面
- 少按钮
- 明确动作主次
- 不像警告框

### 2. 错误态 / degraded
错误态与 degraded 态要保留，但要区分：
- `invalid` 可以更接近阻塞态
- `degraded` 更适合作为聊天中的轻警告，而不是强制把聊天区完全切掉

换句话说：
- **degraded 不应该像崩了**
- 应该像“还能聊，但远程 AI 当前不稳定”

### 3. Active 态
Active 态要把当前实现中的“工具轨迹与浏览器动作留到后续任务再接入”之类过时文案全部替换为真实能力描述，使产品文案与实现一致。

## 消息设计

### assistant
- 视觉上最稳定、最可信
- 气泡宽度不宜过窄
- 文本阅读体验优先

### user
- 更轻、更干净
- 与 assistant 形成明显但克制的区分

### tool_result
- 不做“系统 toast”感
- 更像 AI 的动作回执
- 例如：
  - 已复制标题和链接
  - 已打开新标签页
  - 已刷新当前页面
- 视觉上比 assistant 弱一级，但仍属于聊天流的一部分

### execution trace
- 不像日志
- 不要大块表格
- 建议做成轻胶囊 / 细条目 / 时间线碎片
- 适合临时出现、完成后弱化保留

## 视觉细节

### 1. 颜色
建议继续用深色主题，但更收敛：
- 主背景更纯净
- 强调色更少
- 避免主界面每一层都发光
- 把发光留给关键状态点、焦点输入、执行轨迹的小节点

### 2. 边界和层级
- 更少“满边框卡片”
- 更多靠透明度、模糊、阴影、间距来区分层次
- 让组件之间像一个统一产品，而不是“多个面板堆起来”

### 3. 字体与排版
- 标题更克制
- 正文可读性优先
- 少做大写标签和功能分区感很强的眉题
- 保证中文界面读起来不挤、不硬、不“前端 demo 味”

## 交互原则

### 1. 打开后第一感受
用户打开 sidebar 时，应感受到：
- 这是一个 AI 助手
- 我可以直接开始聊
- 它知道当前页面，但不会一直强调这一点

### 2. 轨迹展示
用户问一个问题时：
- 看到它在读页面
- 看到它在执行动作
- 看到动作完成
- 但整个过程不应该像控制台刷日志

### 3. 状态切换
状态切换需要更柔和：
- locked → active
- active → degraded
- degraded → valid

都应该是产品级状态过渡，而不是突然切换到另一个管理面板。

## 模块影响范围

本轮 UI 主要应修改：
- `src/pages/sidebar/index.html`
- `src/pages/sidebar/index.css`
- `src/pages/sidebar/sidebar-dom-controller.mjs`

必要时少量调整：
- `src/pages/sidebar/index.mjs`
- `src/pages/sidebar/sidebar-state-controller.mjs`

尽量不再大动业务逻辑，把重点集中在：
- 结构层级
- 文案一致性
- 状态呈现
- 视觉语言

## 验收标准

本轮 UI 重设计完成后，应满足：

1. 打开 sidebar 后，第一感觉是“AI 助手”，不是“功能面板”。
2. 顶部状态更轻，不再占据主视觉。
3. 聊天流成为界面核心。
4. 页面信息存在，但不喧宾夺主。
5. 工具执行轨迹保留且可见，但不呈现为重型日志区。
6. 锁定态 / 错误态 / degraded / active 态的产品感明显提升。
7. 整个 sidebar 的高级感、精致感、克制度，明显优于当前版本。

## 实施建议

这一轮应视作 **独立 UI refinement 任务**，不再混入新的协议支持、工具扩展或后端能力改造。目标是把现有已完成的 agent 能力，用更好的产品语言和更高级的视觉表达交付出来。
